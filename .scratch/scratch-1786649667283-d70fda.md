# Seedwise Product Development Roadmap

**Roadmap window:** 13 August–9 September 2026  
**Status:** Working four-week plan  
**Primary objective:** Prove and improve the B2C student-value loop while validating B2B willingness to pay before committing engineering capacity to an institution product.

## Strategy in one sentence

Build one measurable student-value loop, improve it from observed evidence, and add only the minimum event-to-insight B2B bridge after an institution makes a credible paid commitment.

## Product principles for this cycle

1. **Measure before expanding.** Instrument the existing B2C journey before adding broad new functionality.
2. **Improve the loop, not the feature count.** Prioritize the largest observed bottleneck across assessment, result, profile, Direction, experiment, reflection, and return.
3. **Sell B2B before building B2B.** Positive feedback does not unlock production work; a credible paid pilot or Letter of Intent does.
4. **Reuse the shared core.** Assessment, scoring, traits, Directions, and experiments should remain channel-agnostic.
5. **Keep personal and event data separate.** Personal B2C history does not automatically become institution data. B2B receives only explicitly shared event-scoped submissions and aggregate event metrics.
6. **Keep pilot operations proportional.** Build only what is required to run and evaluate one real institution workflow.

# Instrumentation decision

## Decision: use the existing application database first

Use an append-only **Convex `events` table** and a typed `trackEvent()` helper during this four-week cycle.

Do not add PostHog, Amplitude, Segment, session replay, or a second analytics pipeline yet.

### Why

- Convex already owns the relevant anonymous sessions, authenticated users, attribution, and product state.
- Server-side milestone events can be written atomically with the product action they represent.
- Anonymous-to-authenticated continuity is easier to maintain in one system.
- Data deletion and access controls remain in one operational boundary.
- The current need is a reliable funnel query or export, not a full analytics platform.
- The implementation can remain vendor-neutral so sanitized events can be mirrored to a cloud analytics service later.

### Recommended architecture

```text
React Native application
        |
        |-- Product mutations
        |     `-- write durable milestone events in Convex
        |
        |-- trackEvent()
        |     `-- write view and interaction events in Convex
        |
        `-- Later, if justified
              `-- mirror sanitized events to an analytics service
```

### Event schema

Use a strict schema rather than an unrestricted properties object.

```text
name
anonymousId
userId?                    # populated after account claim
assessmentSessionId?
occurredAt
schemaVersion

source?                    # organic | referral | institution
campaignKey?
institutionKey?
institutionEventKey?

directionKey?
experimentKey?
questionIndex?

platform
appVersion
```

Do not store assessment answers, names, email addresses, birthdates, result prose, reflection text, or institution free-text responses in analytics events.

### Initial event taxonomy

```text
entry_opened
assessment_started
assessment_answered       # question index only
assessment_completed
result_viewed
profile_claimed
direction_viewed
experiment_viewed
experiment_started
experiment_completed
reflection_saved
app_opened
```

### Server-side milestone events

Write the event inside the product mutation for:

- assessment started and completed;
- profile claimed;
- experiment started and completed;
- reflection saved.

This prevents analytics from reporting completion when the actual product write failed.

### Client-side interaction events

Use the typed client helper for:

- entry opened;
- result viewed;
- Direction viewed;
- experiment viewed;
- application opened.

### Initial reporting requirement

Do not build an analytics dashboard. Provide one internal query or CSV export that reports:

```text
Entry
  -> Assessment started
  -> Assessment completed
  -> Result viewed
  -> Profile claimed
  -> Direction viewed
  -> Experiment started
  -> Experiment completed
  -> Returned on a later day
```

The output must support:

- conversion between consecutive stages;
- assessment drop-off by question;
- organic versus institution-attributed entry;
- campaign, institution, and event breakdowns;
- anonymous-to-authenticated continuity;
- first return on a later calendar day.

# Four-week roadmap

## Overview

| Week | Main outcome | Engineering emphasis | B2B emphasis | Decision produced |
|---|---|---|---|---|
| **1: Aug 13–19** | Make the current journey observable | Instrument and verify the B2C MVP | Make the pilot offer concrete | Reliable baseline and qualified conversations |
| **2: Aug 20–26** | Test whether the student loop provides value | Complete or fix the smallest meaningful action/return loop | Make explicit paid-pilot asks | Largest B2C bottleneck plus commitment/no-commitment result |

## Week 1 — Make the existing journey observable

**Dates:** 13–19 August 2026

### Outcome

Establish a reliable baseline for the current B2C journey and make the institution pilot proposition concrete enough to test.

### B2C product work

1. Add the typed `events` schema and required indexes.
2. Add the server-side event mutation.
3. Add a vendor-neutral `trackEvent()` client helper.
4. Instrument the existing journey through `experiment_viewed`.
5. Preserve the same `anonymousId` through account claim.
6. Attach source, campaign, institution, and event attribution where available.
7. Add one funnel query or CSV export.
8. Smoke-test the complete MVP journey on a physical Android device.
9. Fix only clear journey blockers discovered during verification.

### B2B product and business work

1. Define one target buyer and one institution event use case.
2. Define the pilot scope and price hypothesis.
3. Prepare one student journey demo.
4. Prepare one sample institution insight or report.
5. Book 3–5 targeted institution conversations.

### Validation runs

Complete controlled runs for:

- organic anonymous entry;
- institution-attributed anonymous entry;
- account-claim flow;
- returning authenticated user;
- abandonment at different assessment questions.

### Exit criteria

- Every controlled journey is traceable end to end.
- Assessment drop-off is visible by question.
- Organic and institution-attributed entry can be separated.
- Anonymous events remain connected after account claim.
- No analytics event contains personal content or free text.
- The existing MVP journey completes on a real Android device.
- A concrete pilot offer, sample output, and target conversation list exist.

### Do not build

- analytics dashboards;
- session replay;
- mentor calls;
- paid B2C tiers;
- content feed or gamification;
- B2B production code.

## Week 2 — Complete and test the action/return loop

**Dates:** 20–26 August 2026

### Outcome

Determine whether students receive the intended payoff and can continue into a meaningful action and return state. Determine whether institutions will move beyond interest toward a paid pilot.

### Default B2C build

Add minimal persisted experiment progress:

```text
userId
directionKey
experimentKey
status                    # started | completed
startedAt
completedAt?
reflectionOutcome?
reflectionNote?           # private product data, never analytics
updatedAt
```

Add:

1. **Start experiment** action.
2. Persisted started state.
3. A **Continue experiment** entry point on Home.
4. Resume behavior.
5. **Mark complete** action.
6. One lightweight structured reflection.
7. Completed state in Home or Me.
8. Events for start, completion, reflection, and later return.

A minimal structured reflection can use options such as:

```text
This felt:
- More interesting than expected
- About as expected
- Less interesting than expected
- Still unsure
```

### Evidence-driven override

Week 1 evidence controls Week 2 implementation. Do not build the experiment loop first if students are not reaching it.

| Largest observed problem | Product response |
|---|---|
| Assessment abandonment | Improve entry framing, question clarity, or flow length |
| Weak result payoff | Improve the result explanation and usefulness |
| Low account claim | Clarify why saving the result matters |
| Directions not opened | Improve the transition and relevance explanation |
| Experiments not started | Improve experiment selection, effort framing, and CTA |
| Experiments start but no return | Improve progress visibility and resume state |

### Student validation

Run a small test with target students. Observe whether they:

- understand the result;
- see why a Direction appeared;
- can choose a realistic experiment;
- understand what starting means;
- know what to do when they return.

### B2B validation

1. Use the sample report to learn what admissions teams would actually use.
2. Make 3–5 explicit paid-pilot asks.
3. For credible demand, lock:
   - named sponsor;
   - institution and target event/date;
   - pilot scope;
   - institution-specific questions;
   - expected output;
   - fee or credible payment signal.
4. Capture objections by buyer, value, price, workflow, and trust.
5. Do not begin B2B production work to help close the deal.

### Exit criteria

- The largest B2C funnel bottleneck is known and addressed or actively tested.
- The action/return loop is measurable wherever users can reach it.
- A user can start, leave, return, resume, complete, and reflect if that is the selected Week 2 build.
- Progress survives application restarts.
- Institution objection patterns are documented.
- The week ends with either:
  - a credible paid commitment; or
  - the B2B production gate remaining closed.

### Do not build

- a general journal or reflection platform;
- streaks, reminders, or notification infrastructure;
- recommendation algorithms;
- broad engagement machinery;
- B2B production functionality before commitment.

## Week 3 — Branch on institution commitment

**Dates:** 27 August–2 September 2026

### Branch A — No credible paid commitment

#### Outcome

Improve the strongest evidenced B2C opportunity and revise the B2B hypothesis without creating a speculative institution backlog.

#### Product work

1. Fix the largest measured B2C bottleneck.
2. Run a second student test after the change.
3. Measure whether the target conversion changed.
4. Update only demo or sales artifacts tied to a concrete institution objection.
5. Keep all B2B production code closed.

#### B2B work

Identify whether the blocker is primarily:

- buyer;
- institution segment;
- offer;
- price;
- report or insight;
- workflow;
- timing;
- trust.

Revise one hypothesis rather than changing everything simultaneously.

#### Exit criteria

- One material B2C bottleneck has been improved or clearly invalidated.
- One B2B objection pattern is supported by multiple conversations.
- The buyer, offer, price, or output hypothesis has been explicitly revised.

### Branch B — Credible paid commitment signed

#### Outcome

Turn the commitment into one concrete event workflow and prove the minimum collection path.

#### Product work

1. Add institution configuration.
2. Add event configuration and attribution.
3. Add QR or event-link entry.
4. Reuse the existing assessment and scoring core in a mobile-web flow.
5. Add the agreed institution-specific question set.
6. Add explicit event-scoped sharing.
7. Persist the event submission.
8. Add minimal B2B funnel events:
   - `institution_entry_opened`;
   - `institution_assessment_completed`;
   - `institution_submission_shared`.
9. Test the complete flow with synthetic data.

#### Exit criteria

One synthetic student can complete:

```text
Event link
  -> Assessment
  -> Result
  -> Institution questions
  -> Sharing choice
  -> Persisted event submission
```

Do not invest in the report surface until the collection path is reliable.

## Week 4 — Prove the complete loop and decide the next cycle

**Dates:** 3–9 September 2026

### Branch A — No credible paid commitment

#### Outcome

Use B2C evidence to make the next investment decision and decide whether to revise or pause the institution track.

#### Product work

1. Measure the Week 3 B2C change.
2. Run another small student test.
3. Examine first-week return behavior.
4. Improve one additional bottleneck only when the evidence is clear.
5. Produce a written recommendation for the next cycle:
   - focus on B2C activation;
   - focus on B2C action/return;
   - test a revised institution buyer;
   - test a revised institution offer;
   - pause B2B.

#### Exit criteria

- The impact of the B2C change is visible.
- The next product bottleneck is identified.
- There is an explicit B2B continue, revise, or pause decision.
- No speculative B2B backlog has been created.

### Branch B — Credible paid commitment signed

#### Outcome

Run the minimum event-to-insight loop and determine whether the sponsor can use the output and wants another event.

#### Product work

1. Add signed or rotatable read-only report access.
2. Add an aggregate event view.
3. Add a student submission list.
4. Add an individual record view.
5. Add CSV export.
6. Add:
   - `report_opened`;
   - `csv_downloaded`.
7. Verify critical scoring and export behavior.
8. Complete browser and device smoke tests.
9. Prepare a short event-day runbook.
10. Run a dry run or live pilot.
11. Fix pilot blockers only.

#### Exit criteria

- Students complete the event flow.
- The institution accesses and uses the output without repeated hand-holding.
- Product usage is distinguishable from concierge assistance.
- The sponsor gives an explicit repeat, renewal, expansion, or decline signal.
- The team has enough evidence to scale, revise, or stop the B2B workflow.

# Success measures

## B2C funnel

Track both counts and conversion rates for:

1. entry opened;
2. assessment started;
3. assessment completed;
4. result viewed;
5. profile claimed;
6. Direction viewed;
7. experiment started;
8. experiment completed;
9. reflection saved;
10. return on a later day.

Avoid setting arbitrary percentage targets before a reliable baseline exists. Week 1 establishes the baseline; Weeks 2–4 aim to improve the largest material drop-off.

## B2B demand gate

A credible commitment requires:

- a named sponsor;
- a specific institution and event/date;
- agreed pilot scope;
- expected output;
- credible intent to pay or an agreed fee;
- willingness to proceed with the minimum pilot workflow.

Friendly feedback, an exploratory meeting, or interest in a future platform does not cross the gate.

## B2B value gate

The pilot produces useful evidence when:

- students complete the event flow;
- the institution opens and uses the output;
- the output supports a real admissions or recruitment task;
- the sponsor can use it without repeated assistance;
- repeat or renewal intent is explicit.

Dashboard polish is not a success measure in this cycle.

# Scope wall

## Build now

- B2C MVP journey verification.
- Acquisition, activation, action, and return instrumentation.
- One internal funnel query or export.
- Small student tests.
- The largest evidenced B2C friction fix.
- Minimal experiment progress and reflection when users reach that stage.
- B2B pilot offer, demo, sample output, and paid-pilot asks.
- Shared-core fixes required by both tracks.

## Build only after credible paid commitment

- Institution and event configuration.
- QR or event-link attribution.
- Mobile-web event entry with no required application install or account.
- Small institution-specific question set.
- Explicit event-scoped sharing and submission storage.
- Signed or rotatable read-only report access.
- Aggregate view, student list, record view, and CSV.
- Minimal event funnel metrics.
- Critical-path checks, browser/device smoke tests, and event runbook.

## Not in this four-week cycle

- Mentor calls or mentor marketplace.
- Paid B2C tiers or payment infrastructure.
- Content feed, streaks, or broad gamification.
- Full B2B dashboard, accounts, or roles.
- Real-time reporting infrastructure.
- CMS, question builder, or institution self-service.
- CRM or enrollment integrations.
- Campaign tooling or notification infrastructure.
- Program or major mapping.
- Fit scoring or recommendation engines.
- Platform infrastructure unrelated to the measured loops.
- Unrelated B2C feature expansion.

# End-of-cycle decision

By 9 September 2026, choose one primary next-cycle direction based on evidence:

1. **B2C activation:** students are not reaching or understanding the result.
2. **B2C action and return:** students receive value but do not act or return.
3. **B2B pilot execution:** a paid commitment exists and the first workflow shows usable institution value.
4. **B2B hypothesis revision:** conversations reveal a specific buyer, offer, price, or output problem.
5. **Pause B2B:** willingness to pay remains weak and further product work is not justified.

The roadmap succeeds when it reduces uncertainty and produces a clear investment decision—not when it maximizes the number of completed features.
